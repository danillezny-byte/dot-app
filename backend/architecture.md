## 2. Стек

### Фронтенд

**Сейчас (PWA):**
- React 18 + Vite (сборщик)
- TypeScript (опционально, добавим позже)
- Tailwind CSS или inline styles (по решению)
- WatermelonDB для офлайн-хранилища
- Supabase JS SDK для работы с бэкендом

**Потом (мобильные):**
- React Native + Expo
- 80% компонентов переедут с веба почти как есть (отличается только базовый набор: `<View>` вместо `<div>`, `<Text>` вместо `<span>`).

### Бэкенд

**Supabase** (Backend-as-a-Service):
- **PostgreSQL** — база данных
- **Auth** — авторизация (email/password, Apple, Google)
- **Storage** — файлы пользователей
- **Realtime** — синхронизация в реальном времени
- **Edge Functions** — серверная логика (Deno runtime)

Регион: **EU (eu-central-1, Frankfurt)**.

## 3. Модель данных

См. `01-database-schema.sql` — там полная схема с RLS-политиками.

**Сущности:**

| Таблица | Что хранит |
|---|---|
| `profiles` | Профиль пользователя (имя, тариф, аватар) |
| `spaces` | Пространства в Базе знаний |
| `pages` | Страницы внутри пространств (с блоками + свойствами) |
| `tasks` | Задачи |
| `habits` | Привычки |
| `habit_logs` | Отметки выполнения привычек |
| `files` | Метаданные загруженных файлов |
| `devices` | Устройства пользователя (для пушей и истории) |

**Ключевые архитектурные решения:**

- **Soft delete:** удалённые записи помечаются `deleted_at`, а не удаляются физически. Позволяет «корзину», восстановление, и не ломает синхронизацию.
- **`updated_at` обновляется триггером:** критично для синхронизации (LWW — Last Write Wins).
- **`shared_with` массив user_id:** заложено сразу для будущего шеринга, без перестройки схемы.
- **RLS включён везде:** даже если украсть anon key, нельзя получить чужие данные. Проверка прав делает сама база.

## 4. Авторизация

**Поддерживаемые провайдеры (поэтапно):**

1. **Email + пароль** — этап 1.
2. **Magic link** (вход по ссылке из письма) — этап 1, бесплатно.
3. **Apple Sign In** — этап 4-5 (требует Apple Developer $99/год).
4. **Google Sign In** — этап 4-5 (бесплатно, но 30 минут настройки в Google Cloud).

**Поток email/password:**

```
1. Пользователь вводит email + пароль на экране Login
2. Supabase.auth.signInWithPassword() возвращает session
3. Session содержит JWT, который автоматически прикладывается ко всем запросам
4. RLS-политики PostgreSQL читают user_id из JWT и фильтруют данные
```

**Поток sign-up:**

```
1. Пользователь регистрируется
2. Supabase создаёт запись в auth.users
3. Триггер handle_new_user() автоматически создаёт профиль в public.profiles
4. (Если включено confirm email) — пользователь получает письмо со ссылкой
```

## 5. Синхронизация (этап 3)

### Подход: Optimistic UI + LWW + Manual Conflict Resolution

```
ДЕЙСТВИЕ: Пользователь добавляет задачу

1. Локально: WatermelonDB сразу пишет задачу с временной меткой now()
2. UI: задача появляется мгновенно
3. Фоном: если есть интернет → POST /tasks в Supabase
4. Сервер: записывает с serverupdated_at = now()
5. Realtime: остальные устройства получают обновление через WebSocket
```

### Конфликт-резолюция

Конфликт = два устройства редактировали одну и ту же запись офлайн, потом синхронизируются.

**Стратегии (по полям):**

| Поле | Стратегия |
|---|---|
| `done` (галочка задачи) | LWW (последний выигрывает) |
| `title`, `notes` (текст) | LWW + если расхождение «драматичное» (>50% разницы) — показать UI выбора |
| `properties`, `blocks` (заметки) | Версионирование + manual UI (экран SettingsSyncConflicts) |
| `position` (порядок) | LWW |

### Библиотека

[**WatermelonDB**](https://watermelondb.dev/) — берёт на себя:
- Локальное хранилище (IndexedDB на вебе, SQLite на мобильных).
- Очередь несинхронизированных изменений.
- Pull/Push с сервером.
- Конфликт-детект.

UI конфликтов мы пишем сами (он уже задизайнен — `SettingsSyncConflicts`).

## 6. Файлы и медиа

**Storage buckets** (создадим в этапе 2):

| Bucket | Что в нём | Доступ |
|---|---|---|
| `avatars` | Аватары пользователей | Публичный read |
| `attachments` | Файлы в заметках/задачах | Приватный, только владелец и shared_with |

**Загрузка:**
1. Клиент → Supabase Storage (multipart upload).
2. После успеха — INSERT в таблицу `files` с метаданными.
3. Storage возвращает signed URL (с ограниченным временем жизни) для отображения.

**Лимиты:**
- Бесплатный тариф: 1 ГБ всего, 50 МБ на файл.
- Если пользователь близко к лимиту — показываем предупреждение.

- Mobile: Expo Push Notifications

## 8. Биллинг (этап 5+)

Когда дойдём до монетизации:

- **Web/Desktop:** [Stripe](https://stripe.com) Checkout — стандарт индустрии.
- **iOS:** in-app purchase через App Store (требование Apple).
- **Android:** in-app purchase через Google Play.

Webhooks от Stripe/Apple/Google → Edge Function → апдейт `profiles.plan`.

⚠️ Apple/Google берут **30%** комиссии на in-app покупках в первый год, **15%** на возобновлениях. Stripe берёт **2.9% + $0.30** за транзакцию.

## 11. Чего намеренно не делаем сейчас

- ❌ Свой бэкенд (Node.js, Go, Python) — Supabase покрывает 95% потребностей.
- ❌ Микросервисы — это для команд из 50+ инженеров.
- ❌ E2E-шифрование — несовместимо с шерингом и AI; добавим опционально для приватных пространств позже.
- ❌ AI-фичи — пользователь сказал «нет» в брифе.
- ❌ Email-маркетинг — отложено до 1k+ пользователей.
- ❌ Realtime collaboration в одной заметке (как Google Docs) — отложено до серьёзных запросов от пользователей.

## 12. Если что-то пойдёт не так

**Supabase упал / отключил аккаунт:**
- Все данные доступны через стандартный PostgreSQL connection string.
- Можно за 1 день переехать на любой PostgreSQL-хостинг (Render, Railway, Fly.io, AWS RDS).
- Auth и Storage придётся переписать на альтернативы (Auth0/Clerk + Cloudflare R2/S3), но фронтенд почти не меняется.

**Нужно масштабироваться (10k+ пользователей):**
- Supabase Pro ($25/мес) → Team ($599/мес) → Enterprise.
- Альтернатива: переезд на свой PostgreSQL + Hasura / PostgREST (бесплатные альтернативы Supabase API-слою).
